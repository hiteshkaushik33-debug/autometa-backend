# Decisions and assumptions

Date: 30 October 2026.

1. Scope is milestone 1 only, following the master brief's explicit immediate task.
   Additional local integration/SMTP requirements amend architecture and later acceptance criteria.
2. Empty workspace means no migration of existing applications and no reusable local code.
   No unrelated directories or applications will be modified.
3. Use npm workspaces, already available, instead of adding pnpm/Turborepo before there is
   a need for task caching. Commit a lockfile. Node 22 is the common runtime.
4. Use Next.js 16, React 19, NestJS 11, Prisma 6, PostgreSQL 16, Redis 7 and BullMQ 5.
   Prisma 6 keeps a single schema-based datasource configuration; a future major upgrade
   needs its own migration review. Resolved package versions are in package-lock.json.
   Official references: [Next.js installation](https://nextjs.org/docs/app/getting-started/installation),
   [NestJS first steps](https://docs.nestjs.com/first-steps),
   [Prisma v6 migration history](https://www.prisma.io/docs/orm/v6/prisma-migrate/understanding-prisma-migrate/migration-histories).
5. No frontend UI libraries are needed for one foundation page. Add Tailwind, shadcn,
   TanStack Query, React Hook Form and charts with the actual dashboard milestone.
6. Local-only development; no Sites registration, cloud publication or production deployment.
7. PostgreSQL is canonical; Redis queues require a transactional outbox at ingestion.
8. Email development order: provider-independent service, mock adapter, Nodemailer Gmail
   adapter, connection test, real test send, BullMQ/rate limiting, inbound processing,
   external sample app, VPS connectivity/limits, transactional-provider migration guide.
   Do not claim real SMTP verification without credentials and explicit test destination.
9. Initially one platform sender whose ownership is verified before enabling Gmail.
   Tenants never control From. Reply-To matching must use server-issued, unguessable
   conversation routing data and authenticated provider ingestion.
10. Gmail SMTP acceptance is not delivery, inbound events or reliable bounce webhooks.
11. Development API keys will be generated by the backend in milestone 2, shown once and
    stored as hashes. No public working key or static seed secret will be committed.
12. No universal Gmail daily quota is assumed. Account limits and VPS outbound connectivity
    must be measured and configured conservatively. Mock configuration currently has no adapters.
13. Production requires TLS/reverse proxy, private service networking, non-root optimized
    images, secret management, backup/restore verification and monitoring; development
    containers are deliberately not presented as hardened production infrastructure.

## Folder separation (31 October 2026)

The user requested top-level backend, admin and users folders. Move the API and worker
to backend/api and backend/worker, and the existing Next.js frontend to users. Keep admin
reserved until its dashboard milestone. Shared packages and repository tooling remain at
the root, and existing npm script names stay compatible.

## Strict three-folder requirement

The user clarified that no root files or folders other than admin, backend and users are
permitted. This supersedes the previous root-workspace arrangement. Backend now owns the
service workspace and all platform tooling; users is an independent npm application with
its own dependencies. No root package, node_modules, environment or Docker configuration
remains. CI YAML is retained under backend as a reference template because GitHub does
not auto-discover a nested .github workflow.

## Authentication/admin increment ? 31 October 2026

User authorized advancing to authentication and admin UI. Use Argon2id, HS256 JWTs with a
random backend-only key, 15-minute access and 7-day absolute rotating refresh sessions.
Store token hashes and session revocation in PostgreSQL; never trust role or tenantId
submitted by a client. Tenant registration creates a backend-controlled 14-day trial.
Add a separate admin Next.js application. Both frontends use an allowlisted server proxy
and separate HttpOnly cookies. Auth links use fragments to keep tokens out of request logs.
Provider-independent preparation plus encrypted mock mail supports local verification/reset;
this is not a completed general outbound EmailService/Gmail integration. Business/event,
provider, billing and deployment milestones remain pending. See phase-2-verification.md.
